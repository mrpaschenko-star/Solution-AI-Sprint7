# Паспорт №18 — извлечение финансовых показателей

## 0. Канвас

| Поле | Решение |
|---|---|
| Ценность | Сократить поиск/перенос полей и выявлять конфликт документов, сохранив контроль андеррайтера |
| Выполнимость | Native parsers + bounded semantic extraction; вычисления/валидация кодом |
| Данные | Эксперты могут разметить источник, период, единицы и значения; правильное кредитное решение не является эталоном extraction |
| Риск | Hallucination, prompt injection, смешение год/квартал и ₽/тыс. ₽; противоречия могут быть реальными |
| Вывод | Берём с условием explicit evidence и human confirmation; без write tools к кредитной системе |

## 1. Триаж

**Гибрид**. [18 инициатив](../Task1/initiatives.md), [полная постановка](../Task1/formulations.md). №2 готовит текст, №18 сопоставляет его с бизнес-словарём. Общая экономия измеряется один раз на сквозном процессе.

## 2. Постановка

| Поле | Значение |
|---|---|
| Бизнес-действие | Андеррайтер подтверждает поля с подсветкой источника и конфликтов |
| Объект и единица | Поле `(application_id, metric_code, period, unit/currency)`; пакет может содержать несколько противоречащих кандидатов |
| Момент | Async по готовому пакету; proposal p95 ≤5 минут для ≤100 страниц; превышение — отдельная очередь |
| Операция | Семантическое извлечение, не генерация отсутствующих финансовых данных |
| Модальность | OCR-текст, layout, native table cells; в MVP модель text-only |
| Выход модели | JSON кандидатов: value string, unit, currency, period, evidence IDs, status |
| Бизнес-выход | Валидированные кандидаты/конфликты для ручного sign-off; расчёт коэффициентов кодом из подтверждённых значений |
| Источник правильного ответа | Экспертная разметка видимого документа с evidence; отсутствующее/нечитаемое/конфликт — правильный отказ |
| Конвейер | OCR/native parser → allowlisted page selection → constrained local LLM для длинного хвоста → schema/evidence/unit/math validation → human confirmation |
| Альтернативная постановка | «Оценить правдивость отчётности/выдать кредит» не входит. Общий RAG по интернету и автономный agent не требуются |

## 3. Оценка качества

| Поле | Значение |
|---|---|
| Бизнес-метрика | Время поиска/ввода/проверки показателей; заявка end-to-end с контролем качества |
| Положительный класс | Не бинарная fraud задача; корректный tuple value+unit+period+source или правильный abstain |
| Метрика под решение | Exact tuple accuracy, precision accepted fields, evidence correctness, conflict recall, coverage и review minutes |
| Baseline | Parser/regex для известных шаблонов + ручной ввод неизвестных; same UI |
| Проверочная выборка | 600 пакетов: 200 known, 150 unseen template, 100 mixed periods/units, 100 missing/conflicts, 50 hostile/out-of-scope; клиент/template split, ≥3 000 целевых полей; 150 dev отдельно |
| Рабочая точка | В модель идут только нерешённые parser поля; accepted candidate требует valid evidence/контракт. Человек подтверждает все критические числа |
| Показатели в точке | Предложения: accepted tuple precision ≥99%, coverage ≥70%, evidence correct 100% проверенного accepted subset; conflict recall ≥95%; 0 выдуманных critical values/успешных tool attacks на challenge set |
| Цена ошибок | Неверные единицы/период могут изменить решение по кредиту; отказ просто сохраняет ручную работу |
| Guardrails | Нет автоматического кредита/отказа, отсутствуют неподтверждённые записи в authoritative системе, нет межзаявочного контекста или утечек |

«100% на наборе» — gate на известных примерах, не доказательство безошибочности production; нужны CI и непрерывный аудит. Confidence LLM не принимается как вероятность верного ответа.

## 4. Готовность данных

| Поле | Значение |
|---|---|
| Решение | Подготовка полей, используемых андеррайтером после подтверждения |
| Объект и гранулярность | Пакет/документ/страница/ячейка → metric tuple + source version |
| Источник и владелец | Архив заявок, словарь показателей/единиц — кредитный бизнес; original files — документооборот |
| Источник правильного ответа | Два андеррайтера независимо фиксируют tuple и источник, арбитр решает смысловые конфликты |
| Доступность признаков в проде | Только документы конкретной заявки, действующий словарь; outcome кредита и последующая просрочка не нужны |
| Разметка | Guide metric scope, periods, currency/scale, precedence; запрещено заполнять пропуск по похожему документу |
| Смещение отбора | Отказы, новые шаблоны и poor OCR должны войти; данные одного клиента/шаблона не размазываются между train/dev/test |
| Репрезентативность | ИП/ООО, разные бухгалтерские системы, годы/валюты, сканы/Excel, конфликтующие версии |
| Объём | Фактически неизвестен. План 600 test +150 dev пакетов, ≥3 000 eval fields; число редких ошибок уточняется inventory |
| Качество | Проверить OCR errors отдельно от extraction, источник/подпись/период, macro/formula injection в Excel |
| Право использовать | Допуск DPO/Legal на inference/evaluation/fine-tuning раздельно; локальный контур, no external API |
| Вердикт | **Разрыв с планом закрытия**: словарь и согласованный guide, корпус и права; pilot после этих gates |

## 5. Карточка эксперимента

| Поле | Значение |
|---|---|
| Где теряем | В длинном хвосте шаблонов и сопоставлении названий показателей |
| Гипотеза причины | Semantic mapping даёт пользу поверх parser на новых шаблонах |
| Конкурирующие объяснения | Ошибка пришла из OCR; исходные документы противоречат; словарь неоднозначен; проблема в UI |
| Рычаг | Context selection, constrained extraction, rules; fine-tuning только после доказанного пробела |
| Дешёвый эксперимент | Parser и parser+Qwen на real OCR и отдельно на идеальной транскрипции, одинаковые пакеты, blind review |
| Ожидаемый эффект | Proposal ≥25% сокращение времени extraction/checking при gates; весь 90-минутный процесс измеряется отдельно |
| Стоимость проверки | 750 пакетов×2×15 мин +20% арбитража×15 мин =412,5 ч; эксперт 1 500 ₽/ч →618 750 ₽; 160 инженерных ч×2 500=400 тыс. ₽; serving после benchmark |
| Критерий остановки | LLM не лучше parser на held-out, precision/evidence не проходят, ручная проверка съедает выигрыш, недопустимый data flow |

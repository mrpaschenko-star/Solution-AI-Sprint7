# Размещение и допуск данных

## Жёсткое отсечение до сравнения

Для реальных данных пока нет решения Legal/DPO/комплаенса о внешнем обработчике. Поэтому внешний маршрут **не активируется**; это статус допуска проекта, не утверждение «все облака незаконны». On-prem тоже требует цели, доступа и retention.

| Вариант | Статус / жёсткий gate | Сравнение оставшегося |
|---|---|---|
| Публичный API модели | Исключён из текущего real-data pilot: не подтверждены договор, регион, subprocessors, retention/training use и lawful purpose | Удобство/качество не компенсирует отсутствие допуска; синтетический benchmark возможен отдельно |
| Выделенный контур провайдера | Условный кандидат после due diligence; «dedicated» не устраняет доступ оператора | Support и стоимость выше, нужны audit/export/exit условия |
| Self-hosting в облаке | Условный кандидат после проверки processing region, support access, backups/logs и договора | Собственные веса и runtime; меньше аппаратной эксплуатации, но остаётся внешняя обработка |
| On-prem банка | **Выбран для пилота и целевого baseline**, при подтверждённых capacity/ИБ gates | Данные/ключи в управляемом банком контуре; затраты эксплуатации и поставки оборудования не нулевые |
| Гибрид по звеньям | В проекте: inference/data on-prem, публичные артефакты моделей через контролируемый импорт | Внешний egress с payload запрещён. Удалённая телеметрия выключена; обновления проходят карантин |

Пилот: изолированная on-prem среда, отдельные service roles, shadow inference, ограниченный corpus. Production: резервированные workers, HA storage, support и restore drill; граф зависимостей тот же, мощности выбираются benchmark. Для №1 CPU, без GPU/API. №2 — CPU baseline, GPU только по замеру. №18 — локальный text LLM candidate; hardware sizing/лицензия/компетенции проверяются до допуска, без требования закупки сейчас.

## Потоки чувствительных данных и решения владельцев

| Поток / граница | Состав и цель | Вопрос и кто отвечает |
|---|---|---|
| TB1 Core/case → аналитический контур | Операции, account/client pseudonyms, суммы, время, сегмент, разрешённые сигналы → признаки и evaluation | Комплаенс/Legal: совместимость с РВК и целью; DPO: representatives/ИП; source owner: minimum fields и retention |
| TB2 сервис → UI сотрудника | Case facts и рекомендации; browser в банковской сети | ИБ: RBAC по расследованию/подразделению, аудит, выгрузки; финмониторинг: полномочия и возражения |
| TB3 registry → production model runtime | Публичные веса/пакеты сначала в карантин; затем signed versions | ИБ/закупки: лицензия, SBOM, hash, уязвимости, no network loaders/telemetry |
| TB4 клиент → document intake | PDF/Excel/фото, банковская тайна/ПДн, скрытые тексты и активный контент | Legal/DPO: основания inference/evaluation и сроки; ИБ: sandbox, no macros, content limits |
| TB5 документы → extraction runtime | Только страницы/ячейки этой заявки; модель не получает ключей/произвольных tools | ИБ: изоляция контекста, provenance, no tool execution; андеррайтер: допустимые поля |
| Возможный внешний перенос | Raw/feature data, embeddings, logs, backups и доступ поддержки — всё входит в карту | Legal/комплаенс/DPO: регион, получатели/субобработчики, договор, обучение, удаление/backup, запросы субъектов; ИБ: ключи, экспорт и аудит |

Псевдонимизация не объявляется анонимизацией: graph/суммы/даты позволяют связывать клиентов. Ключи обратного сопоставления доступны только банковскому сервису по роли. Сроки хранения обучающих снимков, case evidence и legal hold могут отличаться; до пилота утверждаются отдельно.

Никакие данные банка в рамках этой учебной работы внешним моделям не передавались. Прочитаны только задание, шаблон и публичные технические/ценовые источники.
